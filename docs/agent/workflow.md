# Workflow

_How work moves through this project. Generated by /bootstrap-project;
referenced by /start-task on every task._

## Modes

- **GUIDE** — default during bootstrap and at the start of a task: ask
  questions, explain options, recommend a workflow. No spawning, no writes.
- **COORDINATE** — after the user approves a task's workflow/plan: spawn
  read-only role agents (Argus, Athena, Themis, Apollo), validate their
  output, prepare the Codex handoff. Still no production writes.
- **EXECUTE** — only within an approved task, only for the approved scope:
  run the Codex handoff, run verification commands. Anything outside the
  approved scope drops back to GUIDE.

## Standard workflow by task type

| Work type | Workflow |
|---|---|
| Small, low-risk fix | Argus → Codex → Apollo |
| Feature | Argus → Athena → **approval** → Codex → Themis → Apollo |
| UI change | Argus → Athena → **approval** → Codex → Apollo (visual/runtime check) |
| Database/migration | Argus (+ data-integrity check) → Athena → **approval** → Codex → Apollo |
| Audit / harsh review | Parallel Argus + Themis specialists → dedup → user |
| Docs only | Argus → writer → Themis |
| Architecture change | Argus → Athena → independent Themis review → **approval** |
| Engine import / extraction (VoidForge) | Argus (map coupling + license headers + test coverage) → Athena → independent Themis review → **approval** → Codex → Themis (elevated scrutiny) → Apollo (run the imported test suite) |
| Calc-formula change **or** game-data bundling | Argus → Athena → **approval + entry in decisions.md** → Codex → Themis → Apollo |

Bold **approval** = hard stop; do not proceed without explicit user sign-off.

### Cephalon-specific approval gates

Two code paths get elevated treatment regardless of how small the change looks:

1. **Calc-formula changes.** Any change to a damage / enemy-scaling /
   mod-interaction / crit / status / elemental / faction-multiplier formula
   away from VoidForge's behavior. The user cannot eyeball these for
   correctness, so: Athena must show the before/after formula and the source
   of the new value, the user must sign off, and the approval is recorded in
   `docs/agent/decisions.md`. Ported VoidForge tests must still pass (or the
   test change is itself part of the reviewed diff with justification).

2. **Game-data bundling.** Committing bulk Warframe game data (item stats,
   drop tables, relic contents, etc.) into the repo. Requires sign-off on
   source, license compatibility, size/format, and how it will be refreshed.
   Recorded in `docs/agent/decisions.md`.

Also: the calculation engine must stay behind a clean service boundary and
must never depend on React / UI code, and the AI assistant must never compute
Warframe math itself — it calls deterministic engine services. Deviations
from these are architecture-gate matters.

## Codex handoff

Implementation is delegated via `codex exec` using the handoff template in
`~/.claude/skills/start-task/templates/handoff-codex.md`. The handoff prompt
and the resulting diff are both shown to the user — the handoff itself does
not require a separate approval step beyond the plan approval that already
authorized this phase of work, but the diff is reviewed before anything is
committed.

## Git / commit strategy

- New repo, single project (structure — single Next.js app vs. monorepo with
  a separate calc package — to be decided in the first architecture task and
  recorded in `decisions.md`). Default branch `main`; feature branches only
  when a task's plan calls for one.
- Small commits per approved phase, not one giant commit per task.
- No commits without explicit user request, per global default in
  `~/.claude/CLAUDE.md`.
- No remote configured yet. No pushes / PRs until the user adds a remote and
  approves pushing. When VoidForge (AGPLv3) code is imported, the commit that
  introduces it must preserve its LICENSE and attribution/notice files.

## Data safety policy

- No irreplaceable local data yet (empty repo, no database). Nothing to back
  up at bootstrap time.
- Data is treated as **sensitive from day one** by policy: when Supabase auth,
  player-account linking, or inventory import land, revisit this section
  before any destructive operation against the database — add a
  backup/restore procedure, confirm least-privilege DB credentials, and
  ensure player identifiers and account tokens are never logged.
- Bundled game data (if approved) is re-fetchable from its source, so it is
  not "irreplaceable", but its provenance and refresh process must be
  documented alongside it.
